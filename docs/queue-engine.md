# ClinicFlow Queue Engine

The Queue Engine is the authoritative operational state for a clinic queue.

## V1 state flow

```
registered
   ↓ check-in
checked_in
   ↓ enter queue
waiting
   ↓ queue engine
approaching
   ↓ call
called
   ↓ start
consulting
   ↓ complete
completed
```

Temporary/exception states are explicit:

- temporarily_away
- no_show
- rescheduled

## Ordering

Initial deterministic ordering:

1. Explicit, confirmed clinical priority
2. On-time scheduled patients
3. Late scheduled patients
4. Walk-ins

Within a priority class, check-in time is the stable tie-breaker.

Clinical priority is never inferred from symptoms or generated by the queue engine.

## Waiting estimates

The engine uses:

- current consultation elapsed time;
- recent actual consultation durations;
- configured fallback duration.

Patient-facing estimates are ranges, not exact promises.

## Consultation completion

When a consultation completes:

1. Actual duration is recorded.
2. The active consultation is cleared.
3. The queue is recalculated.
4. The next patient is exposed.
5. The resulting snapshot can be published to live clients.
6. A `consultation.completed` event is recorded.

## Event audit

Queue mutations emit events with:

- event ID;
- event type;
- clinic;
- queue entry;
- actor;
- timestamp;
- optional metadata.

This creates the boundary for the later persistence/webhook layer.

## Current implementation boundary

The engine is deliberately independent of:

- database;
- HTTP framework;
- WebSocket/SSE provider;
- WhatsApp;
- SMS;
- MediLoop AI;
- AI Clinical Screening.

The next phase can wrap this engine with persistence and API routes without moving queue rules into the UI.
